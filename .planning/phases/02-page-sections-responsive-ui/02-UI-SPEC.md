# Phase 2 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

## Scope note — read first

**The visual design is 100% locked and final.** Source of truth: `.planning/design-handoff/concept-1a.html`.
Per `.claude/CLAUDE.md`: "Recreate concept-1a pixel-faithfully. Colors, typography, spacing,
rotations, and the hand-drawn treatment are all intentional and final." This UI-SPEC is an
**extraction**, not a proposal — every value below is copied verbatim from the prototype's
`<style>` block/body or from `app/globals.css` (already ported in Phase 1). No design
questions were put to the user; there are no open design decisions except the two gaps the
prototype itself doesn't cover (the visible FAQ section markup, and the support-section's
CSS class names, since that block is inline-styled) — both are resolved below using
**only already-locked tokens and existing class patterns**, never new colors/spacing/fonts.

Builds on Phase 1's `01-UI-SPEC.md` (design tokens, font-loading contract, 60/30/10 color
mapping) — not restated here except where a value is needed inline for a specific section.

**Nav copy → target mapping (defect fix #1):** nav reads exactly "Features · FAQ" (the "How
it works" item is dropped, per ROADMAP/REQUIREMENTS). "Features" links to `#features` (the
"What you can do" band — the section that literally enumerates product capabilities).
"FAQ" links to `#faq`. Both must be real `<a href="#features">`/`<a href="#faq">` elements,
not `<span>`.

**CSS side-effect of the span→anchor fix:** the global rule `a{color:var(--purple)}` will
recolor the nav links unless overridden. Add `.navlinks a{color:inherit}` (excluding
`.btn-ghost`, which already has its own `color:var(--ink)`) to `app/globals.css` so
"Features"/"FAQ" keep the original `var(--body)` nav-link color instead of turning purple.
The existing mobile-hide rule `.navlinks span{display:none}` must become
`.navlinks a:not(.btn-ghost){display:none}` in the 760px media block (selector tag changed
from `span` to `a`) — this is intentional, matches the prototype's original mobile
behavior (in-page links hidden ≤760px, GitHub button stays), not a new a11y gap: hidden
elements are `display:none` (removed from tab order entirely), not a partially-reachable
focus trap.

**This project's spacing deliberately does NOT follow the standard 8-point scale** — same
ruling as Phase 1's UI-SPEC. `.claude/CLAUDE.md` declares the prototype's spacing values
"intentional and final." Every value below is copied verbatim from `concept-1a.html` /

attributes (which Phase 2 must promote into real classes — see Support Section below).

| `.who` | padding `22px 0 40px` | Who-it's-for section |
| `.band .wrap` | padding `38px 0` | Features dark band |

## FAQ Section — New Markup Contract (PAGE-08)

The prototype has **no visible FAQ markup** — only a `FAQPage` JSON-LD block (out of
scope per REQUIREMENTS.md; Google removed FAQ rich results 2026-05-07). Phase 2 must add
a real, visible FAQ section rendering `faqs[]` from `lib/content.ts` as real page text.
Since the prototype sets no precedent for this section's visual structure, this is the
one genuine layout decision in this phase — resolved by reusing the existing `.diff`
heading/column typography (no new tokens, sizes, or colors introduced):

- Section wrapper: `<section class="diff" id="faq">` (reuses `.diff`'s existing padding
  `34px 0 10px` and `.diff h2` heading style — 700 24px Shantell Sans).
- Heading: "FAQ" (or "Frequently asked questions" — copy discretion, keep short to match
  the prototype's terse H2 pattern: "Who it's for", "What you can do", "How it's
  different").
- Each Q&A pair: reuse `.diff .h` (700 14px Public Sans, `margin-bottom:5px`) for the
  question and `.diff .b` (400 13.5px/1.5 Public Sans) for the answer, stacked in a
  single column (`display:flex;flex-direction:column;gap:20px`) rather than the 3-column
  `.diff .cols` grid — six Q&A pairs in three columns would be visually cramped and was
  never validated in the prototype; a single readable column matches the origin-story
  card's single-column precedent immediately below it.
- All 6 entries render in `faqs[]` array order — no reordering, no truncation.
