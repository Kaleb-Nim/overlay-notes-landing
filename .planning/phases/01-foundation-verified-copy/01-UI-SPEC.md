# Phase 1 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

## Scope note — read first

**This is a foundation phase. It builds NO visible page sections.** Nav, hero, feature
cards, FAQ, footer, and every other section in `concept-1a.html` are Phase 2's job. This
UI-SPEC locks the **design-system foundation** every Phase 2 section will consume:
the color-token palette, the two-typeface font-loading contract, and the ruled-paper
background rhythm — plus the copy contract (`lib/content.ts` + verbatim claims) that
Phase 1 is responsible for pre-verifying.

The visual design is **100% locked and final**. Source of truth:
`.planning/design-handoff/concept-1a.html`. Per `.claude/CLAUDE.md`: "Recreate concept-1a
pixel-faithfully. Colors, typography, spacing, rotations, and the hand-drawn treatment
are all intentional and final." Nothing below is a proposal — it is extracted verbatim
from the prototype and `01-CONTEXT.md`. There are no open design decisions in this phase,
so no design questions were put to the user.

## Design System

| Property | Value |
|----------|-------|
| Tool | none — no shadcn, no component registry |
| Preset | not applicable |
| Component library | none — hand-authored semantic HTML + plain global CSS (no Radix/Base UI). Decided in `.claude/CLAUDE.md`: single-page, one-off pixel-tested prototype, no reuse to justify a component library. |
| Icon library | none — the design uses emoji glyphs as icons (📚 🔬 🧠 💻 ✎ ↕ 💾 🌐 ☕ ✦ ↴), plus two hand-drawn inline `<svg>` elements (the hero squiggle underline and the arrow pointing at the screenshot). No icon font, no SVG icon set. |
| Font | Shantell Sans (display / handwritten — headings, brand wordmark, marker-style callouts) + Public Sans (body / UI text) — both self-hosted via `next/font/google` |

**Why not shadcn:** `.claude/CLAUDE.md`'s Styling section already decided this definitively
("Plain Global CSS, Not Tailwind, Not CSS Modules") — every distinctive value in the design
(arbitrary rotation degrees, hard-offset shadows, ruled-paper gradient stops) is off any
utility framework's default scale, and this is a single, already-finished page with no
component reuse to justify a design system tool. The standard shadcn-init gate is
superseded by this explicit project constraint; the user was not re-asked.

## Font Loading Contract (FOUND-03)

| Family | CSS Variable | Weights | Styles | Role |
|--------|--------------|---------|--------|------|
| Shantell Sans | `--font-shantell` | 400, 600, 700 | normal + italic 500 | Display/marker — H1, H2 section headings, brand wordmark, handwritten annotation callouts (`.note-r`, `.note-b`), kicker text, origin-story quote, support-card headline |
| Public Sans | `--font-public` | 400, 500, 600, 700 | normal + italic 400 | Body/UI — paragraphs, nav links, buttons, chips, badges, footer, card labels |

- Google Fonts axes string (from `concept-1a.html` line 37, the confirmed source of truth):
  `Shantell+Sans:ital,wght@0,400;0,600;0,700;1,500` and
  `Public+Sans:ital,wght@0,400;0,500;0,600;0,700;1,400`.
- **Drop Space Grotesk.** The prototype `<link>`-loads it but references it in zero
  `font-family` declarations (0 matches, confirmed by direct grep of the file). Loading it
  would be a wasted request with no visual effect. Only Shantell Sans + Public Sans satisfy
  "every weight/style the design actually uses."
- Both load via `next/font/google` (self-hosted, no render-blocking third-party request),
  each exposed as a CSS custom property and wired into `:root`/`body` so the ported CSS from
  the prototype keeps working with zero selector changes beyond the two `font-family` values.
- CSS variable names (`--font-shantell`, `--font-public`) are this UI-SPEC's naming decision —
  CONTEXT.md left exact naming to Claude's discretion; use these names so Phase 2 doesn't
  need to guess or re-derive them.

## Spacing Scale

**This project's spacing deliberately does NOT follow the standard 8-point scale.**
`.claude/CLAUDE.md` declares the prototype's spacing values "intentional and final" — the
hand-drawn aesthetic depends on pixel-tuned, sometimes off-grid values (e.g. `22px`, `30px`,
`34px`, `38px` padding/gaps throughout `concept-1a.html`'s `<style>` block), not an abstracted
4px system. Forcing them onto an 8pt grid would silently deviate from the locked design.

Phase 1 builds no components, so almost no spacing values are consumed yet. The one
spacing-shaped value this phase **does** implement is the ruled-paper background rhythm
(FOUND-05):

| Token | Value | Usage |
|-------|-------|-------|
| Ruled-paper cycle | 32px | Full repeat unit of the `repeating-linear-gradient` |
| Ruled-paper paper band | 0–31px | Solid `--paper` fill within each 32px cycle |
| Ruled-paper rule stroke | 31–32px | 1px-equivalent `--rule` colored line within each 32px cycle |
| Content max-width | 1120px | `.wrap` container (referenced for any Phase 1 layout shell, e.g. root layout wrapper) |
| Content horizontal padding | 40px | `.wrap` container |

Exceptions: **the 8-point scale itself is the exception** — see rationale above. Phase 2's
UI-SPEC must declare exact per-section spacing sourced verbatim from `concept-1a.html`
(copy the literal px values), never derived from a fresh abstracted scale.

## Typography

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body (default reading text — paragraphs, chip labels, footer) | 16px (browser default; no explicit `font-size` set on `body` in the prototype) | 400 | 1.5 (prototype's hero/body paragraphs use 1.55) |
| Label (nav links, buttons, badges/pills, chips) | 14px (12.5–15px range depending on element) | 500–700 | 1.2 |
| Heading (H2 section headings — "Who it's for", "What you can do", "How it's different") | 24–26px | 700 | 1.2 |
| Display (H1 hero headline) | `clamp(38px, 5vw, 54px)` | 700 | 0.98 |

Font-family mapping (see Font Loading Contract above): Display and Heading roles render in
`var(--font-shantell)`; Body and Label roles render in `var(--font-public)`. This mapping is
fixed by the prototype's per-selector `font-family` declarations, not a general rule to
reapply freely — Phase 2 must match each element's family 1:1 against `concept-1a.html`,
since some small handwritten callouts (e.g. `.note-r`, `.note-b`, the yellow "the story" tag)
use Shantell Sans at label-sized text (14–17px), breaking the naive "headings only" heuristic.

Phase 1 builds no visible UI, so the template's CTA/empty-state/error-state framing maps
loosely — this product also has no forms, no async data loading, and no destructive actions.
What Phase 1 **does** own is locking the exact, verified copy strings that `lib/content.ts`
and Phase 2's rendering must use verbatim.

| Element | Copy |
|---------|------|
| Primary CTA (Phase 2 renders; links to Chrome Web Store) | "+ Add to Chrome" |
| Secondary CTA (Phase 2 renders; links to GitHub repo) | "View on GitHub" |
| Support CTA (Phase 2 renders; links to Buy Me a Coffee) | "☕ Buy me a coffee" |
| Privacy statement (verbatim, locked — CONT-03) | "nothing is collected, transmitted, sold, or shared" — certified Chrome Web Store Developer Dashboard text; must not be reworded, paraphrased, or reordered anywhere it appears |
| Required verbatim phrase (CONT-04) | "excalidraw chrome extension" — must appear exactly, lowercase as shown in the prototype's "vs. Excalidraw" copy, in a natural sentence in visible body copy |
| Support-section claims (CONT-08, reconcile against `STORE-LISTING.md`) | "free and always will be"; "no accounts, no ads, nothing tracked"; solo developer covering hosting/build costs — the "nothing tracked" phrasing must be reconciled against this same site's own Vercel Analytics (cookieless, no individual tracking) so the claim stays defensible; do not silently drop or contradict it |
| Empty state | Not applicable — no lists/collections render with variable data in this product. `lib/content.ts`'s `faqs[]` is a fixed, build-time-authored array of exactly 6 entries; it is never runtime-empty (no fetch, no user input). |
| Error state | Not applicable — no forms, no client-side data fetching, no async operations exist in this static single-page site. |
| Destructive confirmation | Not applicable — this product has no destructive actions (confirmed in `.planning/REQUIREMENTS.md` Out of Scope). |
