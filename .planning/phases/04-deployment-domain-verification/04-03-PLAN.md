It is NOT interpreted as requiring a populated dashboard graph at plan-execution time — Vercel's own docs say the graphs need a few days of visitors, so waiting for them would block the phase on the passage of time. ### Other flagged assumptions

- **Beacon POST timing.** The script *requests* (`script.js` for each product) fire deterministically
  on page load and are asserted. The actual measurement beacon POST is timing- and lifecycle-dependent
  (Speed Insights reports vitals on page-hide), so it is not asserted — asserting it would produce a
  flaky gate. This is why the dashboard-data leg is a backstop rather than an automated check.
- **Enable-then-redeploy ordering.** Both quickstart docs state the tracking routes appear "after your
  next deployment". The redeploy in Task 2 is therefore mandatory, not optional, and running the beacon
  check before it would produce a false 404.
</flagged_assumptions>
